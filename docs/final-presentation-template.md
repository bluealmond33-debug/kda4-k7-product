# 1. Executive Summary

## 1-1. 프로젝트 핵심 요약

### 핵심 메시지

> **은행 고객이 겪는 ARS 탐색과 반복 설명을 줄이고, 상담사가 통화 전후 맥락·위험·규정 근거를 빠르게 확인하도록 돕습니다. 모든 AI 처리는 발표용 폐쇄 LAN의 로컬 서버에서 수행하고, 전사 직후 개인정보를 마스킹합니다.**

| 구분 | 핵심 내용 |
|---|---|
| 문제 | 긴 ARS 버튼 탐색, 오연결·재이관, 상담 맥락 부재, 금융 개인정보의 외부 AI 전달 위험 |
| 해결책 | 자연어 발화 → 실시간 전사 → PII 마스킹 → 요약·라우팅·위험 분석 → 규정 근거 → 상담카드 |
| 데이터 | 감정온도 27,467개 발화, WavLM 고합의 음성 36,665건, 최신 Product 규정 코퍼스 1,607청크(backend 런타임 사본은 1,153청크로 미동기화) |
| 모델 | faster-whisper, EXAONE 3.5 7.8B, eGeMAPS+LightGBM, WavLM, bge-m3+FAISS |
| 서비스 | 고객·상담사·관리자 화면, 실시간 WebSocket 전사, 상담카드, RAG 규정 검색, 후처리 |
| 보안 | 발표 경로 외부 호출 0 목표, 원본 음성 미저장, 전사 직후 PII 마스킹, 개인정보 서비스 분리 |
| 기대 효과 | 반복 질문·잘못된 이관·후처리 시간을 줄일 수 있는 상담사 의사결정 보조 |

> RAG 1,607청크(2026-07-28 기준, 계속 증가 중)는 이 저장소 `database/rag/chunks.jsonl`(원본) 기준이다. backend 런타임 사본(`backend/app/services/rag_data/regulation_chunks.jsonl`)은 여전히 1,153청크로, 간극이 초판 대비 오히려 더 벌어졌다(410청크 → 454청크). 발표 전 `scripts/check_regulation_chunks.py --apply`로 동기화 여부를 반드시 확인한다.

### 현재 구현을 한 문장으로

> **실시간 전사·즉시 마스킹·발화별 WavLM 분노 신호·`#` 입력 시 eGeMAPS+LightGBM(v4) 실행·정책 기반 DTMF 본인인증·통화 종료 상담카드는 모두 이 저장소(모노레포, PR #18 2026-07-24 병합 완료)의 `backend/`에서 확인되며, 남은 정직한 한계는 주민등록번호 마스킹 누락 사례와 무음 구간 STT 환각(둘 다 2026-07-26 기준 미해결 P0), 그리고 본인인증이 실제 고객원장 대조가 아닌 형식 검증이라는 점입니다.**

## 1-2. 프로젝트 아이덴티티

- 팀명: **K7**
- 서비스명: **KARI-NA**
- 미션: **기다리는 콜센터를 준비되는 콜센터로 전환한다.**
- 핵심 키워드: `#NoARS` `#OnPremiseAI` `#PrivacyByDesign` `#AgentAssist`

### 차별점

1. **보이는 온프레미스**  
   STT·LLM·감정·RAG를 로컬에서 구동하고 시연 중 WAN을 분리할 수 있다.
2. **AI가 대체하지 않고 준비**  
   AI는 요약·추천·위험 신호를 제공하고 최종 확인과 조치는 상담사가 수행한다.
3. **개인정보를 분석 전에 차단**  
   STT 직후 마스킹하여 LLM·RAG·DB가 원문 PII를 보지 않도록 설계했다.

# 2. 기획 배경 및 문제 정의

## 2-1. 현재 콜센터의 세 가지 벽

| 문제 | 고객·상담사 영향 | KARI-NA 대응 |
|---|---|---|
| 끝없는 ARS | 고객이 메뉴를 탐색하고 번호를 반복 입력 | 고객은 자연어로 용건을 말함 |
| 맥락 없는 연결 | 오연결·재이관 시 같은 내용을 반복 설명 | 전사·요약·추천 부서를 상담카드로 준비 |
| 금융 개인정보와 AI의 충돌 | 계좌·주민·카드 정보의 외부 전달 우려 | 로컬 AI + 전사 직후 마스킹 + 원본 미저장 |

### 현업 근거

- 프로젝트 저장소의 콜센터 인터뷰 기록에서 **잘못된 부서 연결과 재이관**이 고객 대기와 감정 악화로 이어진다는 문제가 확인됐다.
- 재연결된 상담사가 고객의 앞선 설명을 모르면 고객은 같은 내용을 반복해야 한다.
- 금융 상담에는 계좌번호, 카드번호, 주민등록번호, 인증정보가 포함될 수 있어 외부 클라우드 AI 사용은 별도 통제가 필요하다.

### 현재 손실을 측정할 지표

| 영향 영역 | 현재 문제 | PoC 측정 지표 |
|---|---|---|
| 시간 | 상담 전 용건 파악과 후처리 수작업 | 최초 응대 준비시간, ACW(후처리 시간) |
| 운영 | 잘못된 부서 연결과 재이관 | 이관율, 재이관율, 부서 추천 정확도 |
| 리스크 | 개인정보가 분석·로그에 남을 가능성 | 원문 PII 저장 건수, 마스킹 누락률 |
| 고객 경험 | 반복 설명과 대기 | 반복 질문 횟수, 평균 대기시간, 만족도 |

> 정량적인 시장 규모·비용 절감액은 현재 저장소 근거만으로 확정할 수 없다.  
> 발표에서 임의 수치를 제시하지 않고 PoC 측정 계획으로 설명한다.

## 2-2. 타깃 사용자와 Pain Point

| 항목 | 내용 |
|---|---|
| 1차 사용자 | 은행 콜센터 상담사 |
| 2차 사용자 | 전화를 거는 고객, 콜센터 운영 관리자 |
| 상담사 업무 | 고객 용건 파악, 본인확인, 규정 조회, 조치 안내, 상담 기록 |
| 현재 방식 | 고객 발화를 다시 질문하고 여러 시스템에서 규정·이력을 개별 조회 |
| Pain Point | 맥락 부족, 잘못된 이관, 규정 탐색 시간, 후처리 부담 |
| 원하는 결과 | 연결 전·통화 중 필요한 정보와 근거가 준비된 화면 |
| 성공 기준 | 준비시간·이관율·후처리 시간 감소, PII 원문 저장 0건 |

### 사용자 관점 문제 정의

> 상담사는 고객과 연결되는 순간 용건·위험·필요 절차를 알지 못해 반복 질문과 수작업 조회를 수행한다. 고객은 이미 설명한 내용을 다시 말하고, 잘못된 이관이 발생하면 대기와 불만이 증가한다.

## 2-3. 목표와 해결 방식

| 질문 | 답변 |
|---|---|
| Why | 금융 개인정보를 외부로 보내지 않으면서 상담 준비 자동화가 필요하다. |
| Who | 은행 콜센터 상담사와 전화를 거는 고객 |
| What | 고객 용건 파악, 부서 추천, 위험 신호, 규정 근거, 후처리 기록 |
| How | 로컬 STT·LLM·음성 모델·RAG와 PII 마스킹을 하나의 상담 흐름으로 연결 |

### 프로젝트 목표

- 모델 목표: 음성 격양도와 분노 가능성을 **서로 다른 참고 신호**로 제공

- 보안 목표: 발표용 로컬 경로에서 외부 AI 호출과 원문 PII 저장을 차단
- 운영 목표: AI가 자동 결정하지 않고 상담사의 최종 판단을 지원

### KPI

## 3-2. 데이터 전처리

### 감정온도

`WAV 검증 → stereo를 mono로 변환 → 16kHz 리샘플링 → eGeMAPSv02 88개 특징 → LightGBM`

| 항목 | 처리 기준 | 이유 | 검증 |
|---|---|---|---|
| 입력 형식 | WAV RIFF/WAVE 확인 | 텍스트·손상 파일의 오추론 방지 | 유효하지 않으면 STUB 사유 노출 |
| 채널 | stereo → mono | 모델 입력 통일 | 추론 전 형태 확인 |
| 표본률 | 내부 16kHz | 학습·추론 조건 일치 | Clean/Telephone 동일 파이프라인 |
| 분할 | 23개 화자쌍 5-fold | 같은 화자 기억에 따른 누수 완화 | 시험 화자쌍은 해당 fold 학습에서 제외 |
| 전화 음질 | 8kHz + μ-law 모사 | 전화 유사 열화 안정성 확인 | Clean과 같은 27,467개 비교 |

### WavLM

`오디오 정규화 → WavLM Base+ frozen → encoder 3·6·9·12층 → 시간축 mean/std → 학습형 계층 가중치 → MLP`

- 특징 추출 36,665/36,665건, 오류 0 기록
- 누락·중복·NaN/Inf 무결성 gate 통과 기록
- 화자 독립 외부 검증과 실제 통화 음질 검증은 남아 있다.

### 서비스 데이터

`원본 음성(메모리) → STT 원문(순간 존재) → PII 마스킹 → 마스킹 전사문 → LLM/RAG/DB`

- 원본 음성은 요청 처리 중에만 사용하고 저장하지 않는다.
- LLM과 DB에는 마스킹된 전사문을 전달한다.
- RAG 질의는 원문보다 요약+키워드를 우선하여 PII와 검색 잡음을 줄인다.
- Product의 원본 코퍼스는 2026-07-28 기준 1,607청크(착오송금 반환지원·SG 사고예방·KB 외환/카드 약관 청킹이 추가되며 계속 증가 중)지만, 모노레포 통합 이후에도 backend 런타임 사본은 1,153청크로 그대로다. 발표 실행본에서 `scripts/check_regulation_chunks.py --apply`로 동기화·FAISS 재빌드가 끝났는지 확인하지 않으면 “1,607청크로 검색했다”고 말하면 안 된다.

# 4. AI 모델링 및 검증

## 4-1. 전체 AI 파이프라인

```text
고객 음성
  ├─ faster-whisper → 전사 → PII 마스킹
  │                         ├─ EXAONE → 요약·키워드·부서·위험 플래그
  │                         ├─ 규칙/분류기 → 업무 유형·라우팅
  │                         └─ bge-m3 + FAISS → 관련 규정 근거
  ├─ eGeMAPS + LightGBM → 감정온도 low/medium/high
  └─ WavLM layer fusion → angry 가능성
                     ↓
             judge + fusion
                     ↓
              상담 준비 카드
```

### 모델별 역할

| 모델 | 입력 | 출력 | 운영 역할 |
|---|---|---|---|
| faster-whisper large-v3-turbo | 음성 | 한국어 전사 | ACTIVE |
| EXAONE 3.5 7.8B | 마스킹 텍스트 | 요약·키워드·부서·위험 | ACTIVE |
| eGeMAPS + cumulative LightGBM | WAV | 격양도 3단계 | SHADOW, batch WAV 경로 + 실시간(`#` 입력 시) |
| WavLM 4-layer stats fusion | WAV/발화 | angry 확률·탐지 | SHADOW, 실시간 발화 경로 |
| bge-m3 + FAISS | 요약·키워드 | 규정 검색 결과 | ACTIVE |

> **(갱신, 2026-07-28)** 이전 초판은 "실시간 WebSocket은 발화별 WavLM만 호출하고 v4 감정온도 `.joblib`은 호출하지 않는다"고 적었으나, 현재 코드에서는 **더 이상 사실이 아니다.**  
> `backend/app/ws/call.py`가 recording 구간의 원본 PCM을 세션 메모리에 잠깐 누적해 두고(DB 미저장), 고객이 `#`을 눌러 발화를 마치면 프런트가 `/analyze-text`를 `call_id`와 함께 호출한다. `backend/app/routers/pipeline.py:analyze_text_endpoint`는 이때 그 세션의 누적 PCM을 `_consume_recording_audio()`로 소비해 **eGeMAPS+LightGBM(v4)을 실제로 실행**하고, WavLM은 "격양도는 낮은데 냉정하게 분노를 감지한" 경우에만 결과를 보정치까지 밀어올리는 역할로 결합된다(v4가 1순위 베이스, WavLM은 보정).  
> 단, `call_id` 없이(또는 세션에 누적 오디오가 없이) `/analyze-text`가 텍스트만으로 호출되면 여전히 음향 신호가 없어 STUB로 떨어진다 — 자세한 조건은 §5-3 참고.

## 4-2. 감정온도 모델 실험과 선정

| 후보 | 검증 조건 | Macro F1 | QWK | High Recall |
|---|---|---:|---:|---:|
| emotion2vec LightGBM | 동일 5-fold 후보 비교 | 0.4242 | 0.0919 | 23.69% |
| **eGeMAPS + LightGBM** | 동일 5-fold 후보 비교 | **0.5948** | **0.3594** | **48.63%** |
| 최종 v4 정책 | High weight 1.25, `P(high)≥0.30` | Clean **0.5638** | 0.3307 | **57.58%** |

### 선정 이유

1. 현재 데이터에서 eGeMAPS+LightGBM 조합이 후보 중 가장 안정적이었다.
2. High Recall 최소 55%, High Precision 35% 이상이라는 사전 조건을 만족했다.
3. Clean과 전화 유사 음질의 High Recall 차이를 6%p 이하로 제한했다.
4. 모델 파일과 추론 코드를 SHA-256으로 동결하여 재현 가능하게 했다.

### 최종 설정

| 항목 | 설정 |
|---|---|
| 특징 | eGeMAPSv02 88개 |
| 분류기 | cumulative LightGBM |
| 앙상블 | 화자쌍 5-fold 모델 확률 평균 |
| High 가중치 | 1.25 |
| High 임계값 | `P(high) ≥ 0.30` |
| Peak 보조 규칙 | 0.00, 런타임 비활성 |
| 모델 파일 | `emotion_temperature_demo_final_v4.joblib` |
| SHA-256 | `88e2c3f3e0d85497a3e59a84ac42835ccf8620aab999de27cdb9ff92fc27d4ac` |


## 5-3. WAV 업로드 분석 흐름

### `/api/v1/calls`

`오디오 검증 → STT → PII 마스킹 → EXAONE → v4 감정온도 → judge → 상담카드 → PostgreSQL`

### `/briefing`, `/summarize-call`

`WAV → STT·마스킹 → EXAONE → v4 감정온도 → 텍스트 감정 → 라우팅 → WavLM → fusion → 카드`

### 주의

- **(정정, 2026-07-28)** `/analyze-text`는 더 이상 텍스트를 오디오 바이트 자리에 넣는 스텁 전용 엔드포인트가 아니다. 요청에 실시간 통화의 `call_id`가 실려 있고 그 세션에 recording 구간 누적 PCM이 있으면, 해당 오디오를 소비해 eGeMAPS+LightGBM(v4)을 **실제로** 실행한다(§5-2). `call_id`가 없거나(순수 프런트 데모 등) 세션에 누적 오디오가 없을 때만 음향 신호 없이 STUB로 떨어진다.
- `/emotion`, `/summarize`처럼 텍스트를 오디오 바이트 자리에 그대로 넣는 옛 방식의 호출부는 여전히 유효한 WAV가 아니므로 STUB 폴백이 발생한다.
- `/api/v1/calls`는 내부 감정 계약과 MVP 감정 계약을 각각 생성하면서 동일 WAV 추론이 두 번 실행될 가능성이 있어 성능 최적화가 필요하다.

### 4중 방어

1. **ACTIVE(단, 알려진 결함 있음) — 실시간 PII 마스킹**

2. **ACTIVE(DTMF, 2026-07-28 갱신) + DEMO(pii-service) — 개인정보 서비스 이원화**  
   본인인증 브랜치(`add_authentication`)는 이미 `main`에 병합됨(더 이상 UNMERGED 아님). 실체는 두 트랙 공존: `/ws/ars`의 정책 기반 DTMF 형식검증(통화 흐름에 통합, ACTIVE)과 기존에 문서화됐던 pii-service 원장대조(별도 프로세스·SQLite, DEMO 상태 유지)가 병렬로 존재하며, 상담사 웹이 최종적으로 어느 쪽 결과를 신뢰하는지는 별도 확인이 필요하다.
3. **DESIGN — mTLS·사설 PKI·allowlist**  
   실서비스 서비스 간 상호인증·암호화 설계
4. **ACTIVE — 온프레미스 폐쇄 LAN**  
   발표 설정에서 외부 인터넷 호출 없이 로컬 모델 구동

> “보안이 완성됐다”가 아니라 **마스킹(주민번호 일부 예외)·미저장·로컬 실행은 구현**,  
> 암호화·키관리·접근권한·파기정책은 실서비스 고도화 범위라고 설명한다.

# 6. 비즈니스 가치 및 확장 계획

## 6-1. 기대 효과

> PoC 단계로 아직 파일럿 실측은 없다. 아래는 **확정 성과가 아니라 검증할 목표 방향**이며, 항목마다 근거 수준([실측]/[설계값]/[인용]/[추정])을 표기했다. 시나리오별 상세 산출 근거는 `docs/KPI_BEFORE_AFTER_SCENARIOS.md` 참고.

### 핵심 메시지

AI가 줄이는 건 **”고객이 말하는 시간”이 아니라 상담사의 판단·검색·재확인·후처리 시간**이다. 고객이 상황을 설명하는 시간은 AI 도입과 무관하게 그대로 필요하다. 이 “상담사 처리” 구간은 업계 통계상 평균 처리시간(AHT)의 **약 20~45%**를 차지한다[인용: 지식탐색 5~15%(지식 격차 시 20%+) + 후처리(ACW) 15~30%, §8].

### 대표 시나리오 3개로 본 비즈니스 임팩트 (목표 상태, [설계값]/[추정])

| 시나리오 | 현재 병목 | KARI-NA 개입 지점 | 기대 방향 |
|---|---|---|---|
| 보이스피싱 긴급신고 | 유형 판단+규정 검색이 응대시간 절반 이상 | 부서·업무코드 후보 자동표시, 근거 자동검색 | 지급정지 골든타임(송금 후 30분)[인용] 내 착수 여력 확보 |
| 주택청약(상품 5종) | 재확인 질문, 5종 문서 수기 탐색 | 요약카드가 이미 말한 정보 유지, 180개 청크 유사도 필터링 | 반복 설명·규정 탐색시간 감소 |
| 연금·IRP(신설 업무) | 낮은 숙련도로 긴 탐색, 콜백 재발 | 숙련도 무관 동일 품질 준비카드 | 준비·후처리 시간 표준화 |

### 유일한 비-가상 증거 [실측]

가상 시나리오가 아니라 실제 코드 로그로 확인된 사례: 부서명이 4갈래(taxonomy/LLM 프롬프트/손수 매핑/프런트)로 흩어져 있던 문제로, 보이스피싱 상담의 유의사항 카드에 전혀 무관한 `'주택청약종합저축'`(유사도 0.620)이 섞여 나온 적이 있다(`backend/app/routers/pipeline.py:87`). taxonomy 7개로 통일한 뒤(`500ad1e`) 이 오작동은 재현되지 않는다 — “잘못된 부서 연결”이 실제로 어떤 사고로 이어지는지 보여주는, 이 문서에서 유일하게 가상이 아닌 사례다.

### 회사 KPI에 매핑하면

| KPI | 기대 방향 |
|---|---|
| 평균 상담시간(AHT) | 판단·검색·후처리 구간 단축 |
| 재이관율 | 부서 오배정 하드필터로 감소 |
| ACW(후처리시간) | AI 초안 검수로 작성→검토 전환 |
| 신규 상담사 온보딩 비용 | 숙련도 무관 동일 품질 준비카드로 완화 |

### 왜 현업에서 쓰일 만한가

- **결정하지 않고 준비만 한다** — 상담사가 최종 판단을 유지하므로, 책임소재가 민감한 금융업에서 도입 장벽이 낮다.
- **개인정보가 외부로 나가지 않는다** — 온프레미스·즉시 마스킹이라 별도 클라우드 보안심의 없이 파일럿 착수가 가능하다.
- **숙련도 격차를 표준화한다** — 신설 업무(연금·IRP)처럼 상담사 경험이 얕은 영역일수록 효과가 클 것으로 기대된다.

### 정량 효과의 현재 상태 — 아직 성립하지 않은 전제

- 위 “기대 방향”은 목표 상태다. 무음 환각 전사(B1)·주민번호 마스킹(B2)·STT 지연(B5)·발화종료 인지(B6)·업무코드 매칭 실패율(B3-BE), 5개 미해결 이슈가 남아있는 한(§6-4) 지금 데모가 이미 이렇게 동작한다고 말하면 안 된다.
- 상담시간·비용·손실 절감은 아직 현업 PoC로 측정하지 않았다. 모델 개발 지표(Macro F1 등)를 업무 ROI로 환산하지 않는다.
- 정량 ROI 산정식은 §6-2 참고 — 승수(단축시간·처리비용)를 채울 실측이 아직 없어 산식만 제시한다.
- 발표에서는 “효과를 검증할 수 있는 로그와 지표를 설계했다”는 수준으로 설명한다.

## 6-2. ROI 측정 설계

```text
연간 편익
= (상담 준비시간 단축 × 연간 상담 건수 × 시간당 인건비)
 + (후처리시간 단축 × 연간 상담 건수 × 시간당 인건비)
 + (재이관 감소 건수 × 건당 추가 처리비용)
 - (GPU·서버·모델운영·품질검수·보안 비용)
```

| 항목 | 필요한 데이터 | 현재 상태 |
|---|---|---|
| 준비시간 절감 | 도입 전후 이벤트 로그 | 미측정 |
| 후처리 절감 | ACW 기준선·AI 초안 수정시간 | 미측정 |

| GPU·서버 비용 | 장비 감가·전력·운영인력 | 산정 필요 |
| 품질 검수 비용 | AI 카드 검토·오류 처리시간 | PoC 측정 필요 |

> ROI 수치는 실측 전까지 발표 본문에서 제외하고 산정식만 제시한다.

### 의사결정 원칙

- AI는 **상담사 보조**이며 금융 조치·인증·고위험 판단을 자동 확정하지 않는다.
- 감정온도와 WavLM은 라우팅을 직접 결정하지 않는다.
- 근거가 임계값보다 낮으면 무관한 규정을 보여주기보다 빈 결과를 허용한다.
- 모든 모델 출력에는 실제 모델·STUB·폴백 여부를 표시한다.

## A-5. 예상 질문과 답변

| 예상 질문 | 핵심 답변 |
|---|---|
| 왜 클라우드 LLM을 쓰지 않았나요? | 금융 상담 음성과 PII가 외부로 나가지 않도록 발표 경로를 로컬 모델로 구성했다. |
| 인터넷을 끊어도 정말 되나요? | 모델·폰트·코퍼스를 사전 배치한 로컬 LAN 경로에서 동작한다. 단, 설정이 로컬 모드인지 시작 전 검증한다. |
| 감정온도 성능이 낮지 않나요? | High 경고의 오탐이 많아 자동 판단이 아닌 상담사 참고용 SHADOW로 제한했다. |
| WavLM 0.805와 감정온도 0.564 중 무엇이 더 좋나요? | 타깃과 데이터가 달라 직접 비교할 수 없다. 하나는 분노 이진분류, 다른 하나는 격양도 3단계다. |
| 실제 모델인지 STUB인지 어떻게 아나요? | 응답의 `analysis_source`, `fallback_reason`, 모델 버전과 서버 로딩 로그로 확인한다. |
| 개인정보가 DB에 남지 않나요? | 원본 음성과 STT 원문은 저장하지 않고, 전사 직후 마스킹본만 저장한다. 단, 주민등록번호는 STT가 숫자를 끊어 적으면 마스킹이 빠지는 사례가 있어(2026-07-26 기준 미해결) 100% 보장이라 말하지 않는다. |
| 본인인증은 완성됐나요? | 기능(`add_authentication` 브랜치)은 `main`에 병합됐고 통화 흐름에도 정책 기반으로 자동 연결됐다. 다만 지금은 생년월일 **형식**만 검증하며, 실제 고객원장 대조는 별도 pii-service가 담당하고 AI 백엔드는 이를 호출하지 않는다 — "본인확인 완료"가 실제 신원확인을 뜻하지는 않는다. |
| 모노레포 통합이 끝났나요? | 예. Product PR #18은 2026-07-24 병합 완료됐고, 이 저장소의 `backend/`가 실행 기준이다. 다만 RAG 코퍼스 런타임 사본(1,153청크)은 원본(1,607청크)과 아직 동기화되지 않았다. |
| RAG가 환각을 없애나요? | 환각을 완전히 없앤다고 단정할 수 없다. 점수 하한과 카테고리 필터로 무관한 근거를 줄이고, 근거가 약하면 비우는 정책을 사용한다. |
| 실제 은행에 바로 적용 가능한가요? | 아니다. 현재는 온프레미스 데모/PoC이며 실통화 검증, 보안 통제, 코어망·CTI 연동이 남아 있다. |
