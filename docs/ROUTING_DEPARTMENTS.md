# 라우팅 부서 정리 — 통화를 어디로 배정할까

> 작성일: 2026-07-23
> 관점: **배정(routing)**. 고객 발화를 받아 누가 처리할지 결정하는 축.
> 기준: `CLASSIFICATION-CATALOG.md` (업무코드 35개)
> 짝 문서: [`RAG_DEPARTMENTS.md`](./RAG_DEPARTMENTS.md) — 검색 축

---

## 0. 이 문서의 축

```
발화 → task_code 판정 ─┬─ S/G/E    → 처리 유형 (자동/일반/긴급)
                       ├─ 부서      → 배정 큐
                       └─ handler   → 처리 주체 (AI_CC / HUMAN)
```

`task_code`가 마스터 키다. 나머지는 카탈로그 조회로 따라 나온다.

**검색 축(`business_code`)은 이 문서에서 다루지 않는다.** → `RAG_DEPARTMENTS.md` 참조.
두 문서가 만나는 지점은 **부서**다. `task_code`로 부서가 정해지면, 그 부서의 규정만 검색한다.

## 3. 배정 규칙

- **접두사 = 처리 유형.** `S001`→SIMPLE, `G002`→GENERAL, `E001`→EMERGENCY. 서버 기동 시 검증 권장.
- **E는 SG 전담.** 현재 E 코드 2개가 모두 SG 부서다.
- **handler가 S/G/E에서 100% 파생된다.** `S`→`AI_CC`, `G`·`E`→`HUMAN`으로 예외가 없다.
  향후 "G인데 AI 처리" 예외를 둘 계획이 없다면 `handler`는 파생 필드로 정리 가능하다.
- **긴급은 통화 중 상향될 수 있다.** 최초 분류로 잠그지 않는다.
  일반→긴급 상향은 허용, 긴급→일반 하향은 금지.

## 4. 구조적 문제

1. **S(단순)의 74%가 카드.** 23개 중 17개가 CRD. 자동처리 설계가 사실상 카드 전용이다.
2. **CRD에 G 코드가 없다.** 카드 복합 상담 배정 불가.
3. **INV에 코드가 없다.** 문서만 있고 배정 경로가 없다.
4. **FX가 코드 1개.** 문서 4건 대비 배정 입도가 거칠다.
