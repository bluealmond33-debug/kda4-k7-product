## 1. 개요

### 1.1 한 문장 정의

**상담사 연결이 필요한 금융 문의 고객이 복잡한 ARS를 헤매는 대신 자연어로 용건을 먼저 말하면, 폐쇄망 안의 AI가 이를 전사·마스킹·분류·검색해 상담사에게 근거가 보이는 상담 준비 카드로 전달하는 시스템.**

AI가 상담사를 대체하지 않는다. AI는 **초안을 만들고 상담사가 최종 판단한다.** 시스템 전체가 이 경계 위에 설계되어 있다.

### 1.2 이름

**KARI-NA** = **K**iwoom **A**cademy **R**esponse **I**nnovation · **N**o **A**RS

이름 자체가 제품 주장이다. "ARS를 없앤다" — 번호를 눌러 미로를 헤매게 하는 대신, 첫 발화에서 용건을 받는다.

### 1.3 검증할 핵심 가설

> **상담 전에 고객 발화를 근거와 함께 한 장의 준비 카드로 제공하면, 상담사는 더 빠르고 안전하게 첫 질문과 처리 순서를 결정할 수 있다.**

이 가설 하나만 검증한다. 실제 상담시간 단축·재이관 감소는 **아직 입증된 성과가 아니다.** 현장 비교 실험 전까지 "검증할 기대효과"로만 표현하며, 이 문서와 발표에서 성과로 주장하지 않는다.

### 1.4 세 줄 요약

1. **입력을 바꾼다** — 번호 누르기(ARS) 대신 자연어 발화. 어차피 발생하는 대기시간을 상담 준비시간으로 전환한다.
2. **판단을 보인다** — 요약·업무분류·부서배정·위험도에 항상 근거(전사 원문 / 안전규칙 / 규정 원문 발췌)를 붙인다.
3. **밖으로 안 나간다** — STT·LLM·임베딩·감정·라우팅 전부 로컬. 외부 API 호출 0.

## 2. 문제 정의 및 시장

### 2.1 현행 콜센터의 구조적 문제

| 문제 | 내용 | 누가 겪나 |
|---|---|---|
| **ARS 미로** | 계층형 번호 메뉴 탐색. 용건이 메뉴에 없으면 끝까지 헤맨 뒤 0번 | 고객 |
| **반복 설명** | ARS에서 입력한 내용이 상담사에게 전달되지 않음 → 처음부터 다시 설명 | 고객 |
| **오연결·재이관** | 잘못된 부서 연결 → 재이관 → 재이관된 부서가 다시 질문 → "아까 다 설명했는데 또?" | 고객·상담사 |
| **후처리(ACW) 부담** | 콜 종료 후 상담이력 작성. **후처리 중에는 콜 자동 이입이 막힘** → 다음 콜 기회 상실 | 상담사 |
| **매뉴얼 탐색** | 방대한 규정·매뉴얼에서 근거를 못 찾아 "잠시만요" 반복 | 상담사 |
| **품질 편차** | 대기업 콜센터도 단기·초보 인력 비중이 높아 초기 오안내가 잦음 | 조직 |

### 2.2 현직자 인터뷰 (2026-07-13, 삼성전자 온라인몰 콜센터)

발견 인터뷰에서 확인한 실무 증언 — 우리 문제 정의의 1차 검증 근거다.

- **현장 KPI는 "시간당 처리 콜 수"** 다. 전산이 하루 처리 콜 수를 실시간 카운트한다.
- **후처리가 병목이다.** 상담이력을 한두 줄로 간결·명확하게 써야 하고, 그동안 콜 이입이 막힌다.
- **매뉴얼이 방대하다.** 미숙지 상태로 실전 투입되면 멘트·정보 위치를 못 찾는다.
- **재이관 시 재질문이 고객 분노의 직접 원인**이다.
- **FCR이 관리 대상이다.** 미해결 종료 건은 전산에 남고, 콜백 반복 시 팀장 점검 대상이 된다.

→ 이 5가지가 그대로 우리 기능 3개(상담 준비 카드 / 규정 검색 / 라우팅)의 설계 근거다.

### 2.3 경쟁사 조사 (2026-07-12, 증권 3사 · 보험 7사)

| 유형 | 대표 사례 | 무엇을 하고 있나 |
|---|---|---|
| 상담사 보조 (KMS·요약) | 신한투자증권 AICC, 미래에셋 RAG 어시스턴트, KB증권 AICC | 실시간 STT + 텍스트분석 + 지식검색으로 상담사 지원 |
| 사후 모니터링 | 현대해상, 교보생명, DB손해보험 | 완전판매 모니터링·불완전판매 심사 (녹취 사후 분석) |
| 위험건 선별 | 한화생명 금융사고 예방 경고, 삼성생명 성문 분석 | 접수 내용에서 보이스피싱·명의도용 위험건 자동 선별 |

**공백:** 세 유형 모두 상담이 **시작된 뒤**에 개입한다. **연결 전 단계에서 용건을 구조화해 부서·긴급도로 트리아지하고, 그 근거를 상담사 화면에 함께 띄우는** 조합은 확인되지 않았다.

### 2.4 우리가 다른 점

| 축 | 업계 일반 | KARI-NA |
|---|---|---|
| 개입 시점 | 상담 중 / 상담 후 | **연결 전 (대기시간)** |
| 고객 입력 | ARS 번호 | **자연어 발화** |
| 인프라 | 클라우드 AICC | **완전 온프레미스 (외부 호출 0)** |
| 근거 제시 | 요약 결과만 | **요약 + 규정 원문 발췌 + 검색점수 + 페이지** |
| 개인정보 | 원본 저장 후 접근통제 | **전사 직후 마스킹, 원본 음성 미저장** |
| 성공지표 | 시간당 콜 수 | **ACW·FCR·재이관율·품질편차** |

**온프레미스가 최대 차별점이다.** 금융 민감정보(음성·계좌·상담이력)를 외부로 반출하지 않는다는 것이 설계 전제이며(ADR-0007 · ADR-0011), 실제로 `OPENAI_API_KEY`를 두지 않고 가동한다.

## 3. 타깃 및 사용자

### 3.1 1차 타깃 = 은행 콜센터 (ADR-0004)

복합 문의가 많고 상담 호흡이 길다 → 사전 요약의 효과가 가장 크다. 규정 기반 응대 비중이 높아 RAG 근거 제시의 가치도 크다.

> ⚠️ **한계 명시:** 멘토가 "왜 카드사가 아닌가"를 반문했고, 은행 타깃의 정량 근거는 아직 미확보다. 발표에서 "은행이 최적"이라 단정하지 않고 "1차 검증 대상"으로 표현한다.

### 3.2 사용자 3인

| 사용자 | 화면 | 얻는 것 |
|---|---|---|
| **고객** (핵심 페르소나: 긴급·복잡 금융 문의) | `/customer` — 폰 UI | 번호 누르기 없이 말하면 접수됨. 연결 후 반복 설명 불필요 |
| **상담사** | `/employee` — 데스크톱 콘솔 | 연결 순간 이미 준비된 카드: 요약·요청·누락정보·위험도·체크리스트·스크립트·규정 근거 |
| **관리자** | `/admin` — 관제 콘솔 | 파이프라인 상태, 지식베이스 통계, 규정 문서 업로드·분류정책 관리 |

관리자 페르소나는 ADR 단계에서 보류였으나, 실제 구현에서는 지식베이스 운영 필요성 때문에 관제 화면으로 들어왔다.

### 3.3 사용 시나리오 — 콜 배정 = 즉시 대기열 (ADR-0005)

```
고객 전화
  → [즉시] 대기열 등록 + call_id 발급          ← 대기시간이 여기서 시작
  → AI: "어떤 도움이 필요하신가요?"
  → 고객 자연어 발화 (실시간 스트리밍 STT)
  → [동시 진행] 마스킹 → 분류 → 부서 판정 → 규정 검색 → 카드 생성
  → 고객이 # 입력 = 접수 완료 신호
  → (auth_policy=REQUIRED이면) 생년월일 8자리 본인인증
  → 상담사 연결 — 상담사 화면에는 이미 카드가 떠 있음
```

**핵심 설계:** 대기시간을 없애려는 게 아니라 **대기시간에 일을 시킨다.** 물리적 대기시간 단축은 상담사 수·동시 통화량 등 통제 불가 변수가 많아 우리 기여를 입증하기 어렵기 때문에 KPI에서도 제외했다(ADR-0006).

## 4. 제품 정의

### 4.1 제공 가치

1. **고객** — ARS 탐색과 반복 설명을 없앤다.
2. **상담사** — 첫 질문·처리 순서·근거 규정을 미리 손에 쥔다.
3. **조직** — 후처리(ACW)와 재이관을 줄이고, 신입/숙련 간 품질 편차를 좁힌다.

### 4.2 기능 목록

| # | 기능 | 상태 | 구현 위치 |
|---|---|---|---|
| F1 | 실시간 스트리밍 STT (WebSocket) | ✅ | `ws/call.py`, `services/streaming_stt.py` |
| F2 | 음성파일 배치 STT (WAV·MP3·M4A) | ✅ | `POST /api/v1/calls` |

| F5 | 요약·고객요청·누락정보 추출 | ✅ | Ollama EXAONE |

### 4.3 상담 준비 카드 필수 출력

- 고객 발화 **마스킹 전사문** + 음성 길이
- 문의 요약 / 고객이 실제로 요청한 내용 / 추가 확인이 필요한 정보
- 업무 유형(`task_code`) · 처리 등급(S/G/E) · 담당 부서 · **배정 근거**
- 사고 징후 `low | high` + **판단 근거** (high면 근거 필수 — DB 제약으로 강제)
- 감정온도 `0~100` + 단계(`stable | caution | elevated`) 또는 `unavailable`
- 본인인증 정책(`NOT_REQUIRED | REQUIRED | EXEMPT`) 및 인증 결과
- 상담 전 확인 체크리스트 / 통화 중 단계별 스크립트
- **사용한 규정 문서의 제목·페이지·조항·발췌·검색점수**
- `call_id`, 생성시각, DB 재조회 결과

### 4.4 화면 구성 (4화면 · `src/App.tsx`)

| 경로 | 화면 | 컴포넌트 | 용도 |
|---|---|---|---|
| `/` | 시연화면 (합본) | `<LiveDemo />` | 한 화면에서 전체 흐름 시연 |
| `/customer` | 고객 화면 | `<LiveDemo view="phone" />` | 발표: 고객 단독 |
| `/employee` | 상담사 콘솔 | `<LiveDemo view="desktop" />` | 발표: 상담사 단독 |
| `/admin` | 관리자 관제 | `<AdminDashboard />` | 파이프라인·지식베이스 관제 |

- 고객·상담사·시연화면은 **같은 `<LiveDemo>` 컴포넌트를 `view` prop만 바꿔 재사용**한다. 고객 화면을 고치면 시연화면의 폰 부분이 자동으로 함께 바뀐다.
- `call_id`가 있으면 세 화면이 **중앙 WS 릴레이로 같은 통화 세션을 공유**한다. 발표에서 고객 폰과 상담사 콘솔을 두 기기에 띄워 동시에 움직이는 것이 이 구조 덕분이다.
- 디자인 단일 소스는 `src/styles/tokens.css`. **웹폰트 CDN 0개** — Avenir Next(라틴)·Pretendard(한글)·Material Symbols(아이콘) 전부 self-host라 인터넷 없이 렌더된다.

### 4.5 범위 경계 — 현재 MVP vs 장기 비전

**발표와 문서에서 이 두 열을 섞지 않는다.**

| 구분 | 현재 MVP (실제 동작) | 장기 비전 (미구현) |
|---|---|---|
| 입력 | 웹 기반 실시간 스트리밍 발화 + 음성파일 업로드 | CTI/SIP 실제 전화망 연동 |
| 본인인증 | 생년월일 8자리 **형식 검증** (원장 대조 없음) | 고객 원장 대조, Voice ID |
| 라우팅 | 부서·업무코드 판정 결과 **표시** | 실제 상담사 큐 자동 배정 |
| 규정 | 하나은행 실물 약관 33문서 (예금·대출·외환·연금) | 전 부서 규정 + 사내 매뉴얼 |

## 5. 시스템 아키텍처

### 5.1 완전 온프레미스 — 그리고 그 이유

**KARI-NA는 완전 온프레미스다. 클라우드는 폴백 전용이다.** (ADR-0007 원안 → ADR-0011 확정)

이유는 세 가지다.

1. **금융 민감정보 반출 리스크.** 통화 음성에는 계좌번호·주민번호·거래내역이 그대로 들어 있다. 외부 API에 보내는 순간 반출이다.
2. **실제 도입 가능성.** 은행 콜센터는 망분리 환경이다. 클라우드 전제 시스템은 PoC 이상 진행되지 않는다.
3. **차별점.** 경쟁사 AICC가 전부 클라우드다(2.3 참조).

> **문서-구현 정합성 이력:** ADR-0008(07-14)은 "MVP 데모는 클라우드, 온프레미스는 부가기능"이라 적었으나, 실제 구현은 07-16부터 완전 온프레미스로 진행됐다. 07-23 ADR-0011로 **문서를 구현에 맞췄다.** 이 문서는 ADR-0011 기준이다.

**2026-07-23 실측:** `USE_LOCAL_MODELS=true`, 외부 호출 0, `DATABASE_URL`=네이티브 PostgreSQL `localhost:5432`.

### 5.6 실행환경 결정 — pgvector vs FAISS, 도커 폐기

두 개의 실행환경 결정이 있었고, 둘 다 "설계 표준"과 "데모 실행"을 분리하는 방향이다.

| 결정 | 설계 표준 | 데모 실구동 | 이유 |
|---|---|---|---|
| 벡터저장소 (ADR-0010) | **pgvector** | **FAISS 인메모리 폴백** | Postgres 하나로 벡터+원문+필터 통합이 목표. 단 도커를 폐기해 pgvector 컨테이너를 띄우지 않으므로 `pgvector_ready()=False` |
| 배포 (2026-07-23) | 컨테이너 | **호스트 직접 실행** | WSL2/Docker Desktop 설치·유지 부담 대비 이득 없음 |

**pgvector 스키마와 하이브리드 검색(의미+키워드, supersede) 코드는 구현 완료 상태다.** 실서비스에서는 DB만 붙이면 전환된다. 코드가 자동 폴백하므로 데모는 인프라 0으로 구동된다.

> 발표 표현: **"설계는 프로덕션급, 시연은 이식성."** 이것을 숨기지 않고 명시한다.

### 6.1 STT — faster-whisper

- 모델: `large-v3-turbo` (온프레미스 GPU) / CPU 노트북 폴백 `small` + `int8`
- 실시간 경로: WebSocket 청크 스트리밍 (`streaming_stt.py`)
- **반복음 환각 필터** (`transformers_stt.py`) — Whisper 계열이 무음·잡음 구간에서 같은 문장을 반복 생성하는 현상을 후처리로 제거
- 마이크 자동이득(`autoGainControl`) 적용, 접수 완료 후 실마이크 차단

### 6.2 업무 분류 및 라우팅 — 3단계 캐스케이드

**분류 축 정의**

```
발화 → task_code 판정 ─┬─ 접두사 S/G/E → 처리 유형 (단순/일반/긴급)
                       ├─ 부서          → 배정 큐
                       └─ handler       → 처리 주체 (AI_CC / HUMAN)
```

`task_code`가 마스터 키다. 나머지는 카탈로그 조회로 파생된다. `S`→`AI_CC`, `G`·`E`→`HUMAN`으로 예외가 없다.

**3단계 판정**

| 단계 | 방식 | 특성 |
|---|---|---|
| 1 | **키워드 규칙** (`routing/classifier.py`) | 외부 파일 의존 0 · 즉시 동작 · 결정적 |
| 2 | **로컬 ML 주제 분류** (`.joblib`, NIA 은행 일반업무 10종) | 모델 파일 있을 때만 활성 · SHA-256 검증 후 로드 · **decision margin ≥ 0.75만 채택**, 미만은 `G004` 폴백 |
| 3 | **로컬 EXAONE 재판정** | `G004`(기타)로 떨어진 경우에만 호출. "카드를 잃어버렸어요"처럼 키워드 목록에 없는 자연어 표현이 전부 G004로 뭉개지는 문제 해결. G004일 때만 호출하므로 흔한 표현의 응답속도에는 영향 없음 |

**금융사고 안전 규칙의 고위험 라우팅이 항상 이 결과보다 우선한다.**

### 6.3 RAG — 규정·매뉴얼 검색

#### 6.3.1 두 축의 만남

```
[통화 쪽]  task_code → 부서 · business_code  ─┐
                                              ├→ 매칭 = RAG 검색
[문서 쪽]  PDF → 전처리 → 부서 · business_code ─┘  (미리 태깅됨)
```

**만나는 지점은 `부서`와 `business_code`다. S/G/E는 만나지 않는다.**

문서에 `task_code`를 붙이지 않는 이유: 문서 1건이 여러 용건에 답한다. 대출 상품설명서 1건이 `S005`·`G002`·`G008`·`G009` 모두에 쓰인다. `task_code`를 붙이면 리스트가 되고 용건이 늘 때마다 재태깅해야 한다. `business_code`가 그 묶음이라 문서 입도에 맞는다.

S/G/E를 검색 필터로 쓰지 않는 이유: 문서는 **주제**로 정의되지 처리 등급으로 정의되지 않는다. 대출 약관은 `G` 통화에도 `E` 대출사기 상담에도 필요하다. 실제로 검색 SQL의 필터는 `categories` 하나뿐이다.

```sql
AND (%(category)s::text IS NULL OR %(category)s::text = ANY (d.categories))
```

#### 6.3.2 코퍼스 — 하나은행 실물 약관

| 부서 | business_code | 문서 | 청크 |
|---|---|---:|---:|
| LON 여신·대출 | `loan` | 21 | 880 |
| DEP 수신·예적금 | `subscription` | 5 | 180 |
| FX 외환 | `fx` | 4 | 61 |
| INV 연금·투자 | `pension` | 1 | 29 |
| SG 사고·신고 | `misremit` | 1 | 11 |
| DEP 수신·예적금 | `deposit` | 1 | 3 |
| CRD 카드·결제 | `card` | **0** | **0** |
| EFN 전자금융 | `efn` | **0** | **0** |
| ETC 기타·공통 | `general` | **0** | **0** |
| **합계** | | **33** | **1,164** |

- 하나은행 PDF 32건 → 1,153청크 + 보이스피싱 사례집 1건 → 11청크
- 데모 시드 34청크 포함 시 총 1,187
- 스캔본(`발행어음.pdf`)은 **PaddleOCR** 처리
- **더 이상 더미가 아니다.** 07-23 E2E에서 실제 약관 검색을 확인했다.

#### 6.3.3 청킹·태깅 기준

**청킹 규칙**
- 구조 마커(`◇`, `제N조`, `①~⑳`) 기준 분리
- **표는 별도 마크다운 청크**로 분리 (본문 청크와 섞지 않음)
- 중복 해시 제거
- 1,200자 캡
- 텍스트-only 콘텐츠(사례집)는 자연 경계(사례·항목) 단위로 1청크

**청크 필드**

| 필드 | 값 | 검색 사용 |
|---|---|---|
| `department` | DEP·LON·FX·INV·SG | ✅ `categories` 필터 |
| `business_code` | deposit·subscription·loan·fx·pension·misremit | ✅ `categories` 필터 |
| `routing` | G(32건)·E(1건) | ❌ 미사용 (태깅만 됨) |

| `entities` | 법령·서식코드·개정일 | 보조 |
| `text` | 맥락 헤더 + 본문 | 임베딩·키워드 대상 |

#### 6.3.4 검색 — 하이브리드

- **의미 검색**: bge-m3 1024차원 임베딩 · 코사인 유사도
- **키워드 검색**: PostgreSQL `ts_rank(tsv, plainto_tsquery(...))`
- **점수 융합**: 두 점수를 명시적 가중치로 결합 (튜닝 가능하게 상수 분리)

### 6.4 감정온도 — 음향·텍스트 융합

#### 6.4.1 두 축 분리 원칙

```
텍스트 축: STT 텍스트만 전달  → 내용·상황 심각도
음향  축: 동일 원본 음성만 전달 → 격앙도·분노
```

**STT 텍스트·키워드·문자열 바이트를 음성 감정 모델 결과로 사용할 수 없다.** 두 결과는 `call_id`로만 결합하며, 음성 결과의 `external_session_key`가 `call_id`와 다르면 **저장을 거절한다** (다른 통화 결과 혼입 방지).

#### 6.4.2 모델 구성

| 축 | 모델 |
|---|---|
| 음향 격앙도 | **eGeMAPS 88특징 + LightGBM** (박정운) |
| 음성 분노 | **WavLM** 레이어 융합 (CPU 격리) |
| 텍스트 감정 | 로컬 EXAONE (`text_emotion.py`) |

- **`recent_anger` (EMA) 도입** — 통화 전체의 `max_anger`를 쓰면 값이 41도에 고정되던 문제를 지수이동평균 기반 최근 구간 반영으로 수정 (`9c4e419`)

#### 6.4.3 정책 결합기 (`fusion.py`) — 4단계 에스컬레이션

| 순위 | 조건 | 결과 |
|---|---|---|
| 1 | 명시적 고위험 룰 적중 (`risk_flags`) | **HIGH** (judge.py 담당) |
| 2 | `situation_severity=high` **+ 근거 있음** | 최소 HIGH까지 승격 |
| 3 | 강한 감정 표현 + `urgency_score` 높음 | 최소 MEDIUM까지 승격 |
| 3b | WavLM 음성 분노 감지 | 최소 MEDIUM까지 승격 |
| 4 | 음향 격앙도만 높음 | 판정 유지, 우선순위만 보조 |

**설계 원칙 3가지**

1. **에스컬레이션 전용.** 더 높은 위험을 시사하면 올리고, 신호가 조용하다는 이유로 이미 나온 판정을 **절대 내리지 않는다.**
2. **감정은 HIGH를 강제하지 못한다.** HIGH는 사고위험 규칙(1·2) 전용, 감정은 최대 MEDIUM. → **"목소리가 크다"는 이유로 고위험이 되지 않는다.**
3. **"냉정한 분노(cold anger)" 대응.** 격앙도는 낮은데 분노만 잡히는 케이스는 격앙도(judge)가 놓친다. 3b 부스터가 유일하게 잡되, 격앙도 값을 덮어쓰지 않고 주의등급만 올린다.

`voice_anger`가 `None`이면 아무 동작도 하지 않아 기존 텍스트 전용 동작과 완전히 동일하다(하위호환).

### 6.5 본인인증

#### 6.5.1 정책 3분류 (`auth_policy`)

`task_code` 기준으로 자동 판정된다. **S/G/E와는 다른 축이라 병행 신호로 붙는다.**

| 정책 | 대상 | 동작 |
|---|---|---|
| `NOT_REQUIRED` | 목록 밖 S/G 업무 (기본값) | 접수 단계에서 인증 없이 받는다. 통화 중 실제 조회·변경으로 의도가 바뀌면 상담사가 그때 요청 |
| `REQUIRED` | 계좌/카드 상태나 출금권한이 **실제로 바뀌는** 업무 — 한도 상향·비밀번호 변경·재발급·자동이체·제한계좌 등 (S105·S106·S111·S112·S115·S120~S127·G001·G003·G004·G006·G007) | 상담사 연결 **직전** 실행 |
| `EXEMPT` | **E001 보이스피싱 신고 · E002 이상거래 신고** | **본인확인보다 긴급 연결이 우선** — 인증 절차 자체를 건너뜀 |

`EXEMPT`가 이 설계의 핵심이다. 보이스피싱 신고 전화에 생년월일부터 요구하면 그 시간이 곧 피해액이다. 구 프론트 호환 필드 `auth_required`는 `REQUIRED`일 때만 `true`이며, `EXEMPT`를 즉시 키패드로 해석하지 않도록 분리했다.

#### 6.5.2 인증 흐름 (`ws/ars.py`)

- 생년월일 8자리 DTMF 입력 → **유효한 날짜 형식(YYYYMMDD)인지 검증** → 불일치 시 안내 음성 후 재입력
- **접수 종료용 `digits` 버퍼와 인증용 `auth_digits` 버퍼를 완전히 분리** — `awaiting_auth` 동안 들어오는 DTMF는 인증 버퍼로만 쌓인다
- 재연결 유예 6초: 소켓이 `call_end` 없이 끊겨도(와이파이 순단·탭 닫힘·새로고침) 즉시 종료로 치지 않고, 같은 role이 재연결하는지 본 뒤 판정
- 접수 종료 신호는 **명시적 `#` 키패드 입력** — 침묵·연결끊김 기반 암묵 추정을 쓰지 않는다(현장 피드백: "전화를 끊었음을 인지할 수 있는 기준"이 필요)

> ⚠️ **경계:** 대조할 고객 원장이 없어 **형식 검증만** 한다. 진짜 신원 대조가 아니며, 발표에서 "본인확인 완료"라 표시하지 않는다.

### 6.6 개인정보 보호 (`pii_guard.py`)

#### 6.6.1 PII 범위 — 11종

| 코드 | 대상 | 코드 | 대상 |
|---|---|---|---|
| `rrn` | 주민등록번호 | `passport` | 여권번호 |
| `card` | 카드번호 | `driver` | 운전면허번호 |
| `account` | 계좌번호 | `biz` | 사업자등록번호 |
| `phone` | 전화번호 | `email` | 이메일 |
| `birth` | 생년월일 | `name` | 이름 |
| `auth` | 인증정보(OTP·비밀번호·보안카드) | | |

#### 6.6.2 설계 원칙 4가지

1. **원본 최소 · 마스킹 우선 (fail-safe).** 애매하면 마스킹한다. 개인정보를 흘리는 것보다 과마스킹이 안전하다. 단, 금액·개수 같은 짧은 숫자는 PII 모양(자릿수·문맥)일 때만 건드린다.
2. **AI는 원본 PII를 보지 않는다.** 실시간 전사는 **상담사에게 팬아웃되기 전에** 마스킹된다. 이후 분석·저장은 전부 마스킹본 기준이다.
3. **휘발.** 원본 음성은 메모리에서만 쓰고 폐기한다. 저장하는 전사는 마스킹본뿐이다.
4. **격리 유지.** `pii_guard`는 PII 저장소를 직접 참조하지 않는다. '아는 고객명 대조'가 필요하면 호출자가 `known_names`로 넘긴다. → **AI 백엔드와 개인정보 저장소의 분리가 유지된다.**

#### 6.6.3 탐지 — 구체 → 일반 우선순위

패턴을 구체적인 것부터 배치해 겹칠 때 앞선 패턴이 이기게 한다(애매 처리).

```
rrn(6+[1-4]6자리) → driver(2-2-6-2) → card(4-4-4-4) → biz(3-2-5)
→ phone(01X-3~4-4) → passport(영1+숫8 / 영2+숫7) → account → email → name
```

- **이름 탐지**는 실제 성씨 gazetteer(김이박최정강조윤장임…)로 시작할 때만 후보로 봐 오탐을 줄인다.
- **계좌번호 3중 패턴**: ① 구분자 있는 3그룹 ② 구분자 없는 10~14자리 ③ **'계좌번호' 문맥어 뒤 9자리 이상**

#### 6.6.4 실제로 잡은 취약점

07-23 시연 테스트에서 **쉼표 형식 계좌번호(`111,222,334`)가 마스킹을 우회**하는 것을 발견했다.

문제의 성격: 쉼표 3자리 묶음은 금액(`10,000,000`)과 **구조가 완전히 동일해 모양만으로 구분할 수 없다.** STT가 숫자를 이렇게 끊어 적기 때문에 실제로 발생한다.

해결: 구분자 집합에 쉼표를 추가하고, 모양으로 판별 불가한 경우는 **문맥어에 기댄다.** `'계좌'` 단독이 아니라 `'계좌번호'`를 요구해 "계좌 잔액 1,000,000원" 오탐을 피했다. **회귀 테스트 추가 완료**(`backend/tests/test_pii_guard.py`).

#### 6.6.5 화면 표시

실시간 전사 마스킹 건수를 **상담사 화면 배지로 표시**한다(`d114f5f`). 마스킹이 조용히 일어나는 게 아니라 "몇 건을 가렸다"가 보인다.

## 8. 판단 경계 및 리스크

### 8.1 반드시 지키는 판단 경계

이 7가지는 코드·DB 제약·문서 모두에서 강제된다.

1. **AI는 초안을 만들고 상담사가 최종 판단한다.**
2. **위험도는 고객 발화의 사고 징후와 안전 규칙으로 판단한다.** 목소리가 크다는 이유로 고위험·감정 고조로 분류하지 않는다 (fusion.py 원칙 2로 강제).
3. **감정 모델이 연결되지 않으면 점수를 만들지 않고 `unavailable`로 표시한다** (DB `unavailable_emotion_chk`로 강제).
4. **시연용 가이드를 실제 은행 내부 규정이라고 소개하지 않는다.** 실물 약관 부분과 시연용 시드를 구분해 말한다.
5. **지급정지·계좌 차단·본인확인 완료·고객 원장 조회를 실제 수행했다고 표시하지 않는다.**
6. **`high` 판정에는 반드시 근거를 붙인다** (DB `high_risk_reason_chk`로 강제).
7. **일반업무 10종 모델의 성능 수치를 긴급·단순·일반 전체나 ARS 17종 라우팅 성능으로 확대 해석하지 않는다.**

### 8.2 보안·규제 고려

| 항목 | 현재 | 향후 |
|---|---|---|
| 데이터 반출 | 외부 호출 0 (전 레이어 로컬) | 유지 |
| 개인정보 | 11종 실시간 마스킹, 원본 음성 미저장 | 마스킹 사전 성능 평가 |
| 망 격리 | 데이터 처리망 내부화, 프론트 8080만 LAN 공개 | 실제 망분리 환경 검증 |
| 전송 보안 | mTLS·allowlist·Pydantic 검증 설계 완료 (`03 Research/2026-07-19`) | 운영 적용 |
| 권한·감사 | 12테이블 설계 보존 (`counselor_permissions`, `access_logs`) | 활성화 |
| 모델 무결성 | `.joblib` SHA-256 검증 후 로드 | 서명 검증 |

### 8.3 리스크와 대응

| 리스크 | 영향 | 대응 |
|---|---|---|
| **방언 오인식** | "부산인데요" → "불타인데요" 재현 | **미해결.** 8.4 참조 |
| 발표 당일 GPU·Ollama 미기동 | 데모 불가 | `STUB_MODELS=true` — GPU·Ollama·외부 API 없이 화면 흐름만 재현 |
| 시연 시나리오와 RAG 커버리지 불일치 | 무관한 규정 반환 | 예금·대출·외환·연금 시나리오로 전환 (9.3) |
| 동기식 요청의 긴 대기 | 체감 지연 | 구조 개선 대상으로 식별. 실시간 WS 경로가 완화 |
| `taxonomy.py` 12코드 vs 카탈로그 35코드 불일치 | 분류 누락 | 정리 필요 (미착수) |
| 레거시 OpenAI 경로 잔존 | "온프레미스라면서 왜 OpenAI 키?" 질문 | README·ADR-0011에 레거시로 명시. 발표 후 제거 |

### 8.4 방언 — 해결 못 했고, 그렇게 말한다

**상태: 미해결. 단 원인 규명 완료 (2026-07-21 조사).**

- 로컬 구동 가능한 **한국어 방언 특화 STT 모델은 존재하지 않는다.**
- 저비용 해법(`initial_prompt`, `hotwords`)을 **실측했고 전부 실패했다.** 프롬프트는 발음 인식이 아니라 **표기 스타일만** 유도하기 때문이다.
- 유일한 경로는 **파인튜닝**이다. AI Hub 권역별 방언 데이터를 확인했다 — 경상(119)·전라(120)·제주(121)·충청(122), 각 3,000시간, 표준어 대응쌍 포함, IRB 불필요·일반 다운로드. **신청 필요(미착수).**

> **발표 포지셔닝: "해결됨"이 아니라 "한계 + 로드맵".** 실측해서 안 됐다는 것과, 되는 경로가 무엇인지를 함께 말한다.

## 9. 성과 지표

### 9.1 확정 KPI (ADR-0006)

**1순위 — 회사·상담 업무 KPI**

| 지표 | 방향 | 우리 기능과의 연결 |
|---|---|---|
| **ACW** 후처리시간 | ↓ | 상담카드가 이력 초안 제공 → 다음 콜 이입 재개가 빨라짐 |
| **AHT** 평균 상담처리시간 | ↓ | 연결 시점에 맥락 파악 완료 |
| **FCR** 첫 통화 해결률 | ↑ | 규정 근거 즉시 제시로 "잠시만요" 감소 |
| **Transfer Rate** 재이관율 | ↓ | 부서 배정 정확도 + 배정 근거 표시 |
| **Calls per Agent** | ↑ | ACW 절감의 결과 지표 |
| **Quality Variance** 상담사별 품질 편차 | ↓ | 신입도 같은 근거·스크립트를 받음 |

**2순위 — 고객 경험 KPI**
ARS 탐색시간 ↓ · 반복 설명 ↓ · 체감 대기시간 개선 · 고객만족도 ↑ · 재통화율 ↓

**제외 — 실제 물리적 대기시간**
상담사 수·동시 통화량 등 통제 불가 변수가 많아 **우리 기여를 입증할 수 없다.** 의도적으로 뺐다.

> ⚠️ **`Calls per Agent` 주의:** ADR-0002는 "시간당 콜 수"를 **단독 목표치로서** 폐기했다. 여기서는 **결과 지표**로만 쓰며, FCR·Quality Variance와 **함께** 볼 때만 유효하다. 단독 극대화는 품질 저하를 유도한다.

### 9.2 현재 측정된 값 vs 검증 예정

| 구분 | 항목 | 값 |
|---|---|---|
| **측정됨** | 업무분류 정확도 (일반업무 10종) | 74.2% / 고확신 구간 90.4% (커버리지 61.3%) |
| **측정됨** | RAG 코퍼스 규모 | 33문서 · 1,164청크 (실물 약관) |
| **관찰됨** | E2E 처리시간 | CPU 노트북 · EXAONE 2.4B 반복 실행 기준 **1분 49초 ~ 2분 46초** |
| **검증 예정** | ACW·AHT·FCR·Transfer 개선폭 | 현장 비교 실험 필요 |
| **검증 예정** | 실제 발화 기준 라우팅 정확도 | 별도 평가 필요 |
| **검증 예정** | 마스킹 정밀도·재현율 | 정량 평가 미실시 |

> **E2E 처리시간은 소수 관찰값이지 성능 보장 수치가 아니다.** GPU 환경·`large-v3-turbo`·`exaone3.5:7.8b` 조합의 실측은 별도다.

### 9.3 데모 완료 기준

다음을 **모두** 충족해야 "동작하는 MVP"라고 말한다.

- [ ] 정상·사고 의심·대출·전자금융 등 승인된 한국어 음성 **10건 이상**이 끝까지 처리된다
- [ ] 모든 응답이 `mvp-1.1` 계약을 통과하고 POST와 GET의 `call_id`·카드가 일치한다
- [ ] 고위험 시나리오에서 사고 징후와 상담사 확인 절차가 누락되지 않는다
- [ ] 카드의 주요 사실이 전사문·안전규칙·표시된 RAG 자료로 **추적 가능**하다
- [ ] 모델 장애·DB 장애·미지원 파일에 대해 거짓 fixture가 아니라 **명확한 오류**가 보인다
- [ ] 인터넷을 끈 상태에서 서버 노트북과 같은 LAN의 다른 기기에서 데모가 열린다
- [ ] 실제 은행 연동이 아닌 기능에는 **데모·미연동 라벨**이 보인다
- [ ] 전사 화면에 마스킹 건수 배지가 보인다
- [ ] 시연 시나리오의 `business_code`에 실물 규정이 존재한다 (**예금·대출·외환·연금** 권장)

## 마무리 — 이 기획서가 지키는 원칙

이 문서는 **할 수 있는 것과 없는 것을 섞지 않는다.**

- 온프레미스는 **실측했다** (`USE_LOCAL_MODELS=true`, 외부 호출 0).
- 규정 RAG는 **실물이다** (하나은행 33문서), 그리고 **63%의 업무코드에 문서가 없다**는 것도 같이 적었다.
- 분류 정확도 90.4%는 **고확신 구간 61.3%에 한한 값**이라고 매번 붙였다.
- 방언은 **실패했다고** 적었고, 무엇을 시도했고 왜 안 됐는지를 남겼다.
- KPI 개선은 **아직 측정하지 않았다**고 적었다.

이 경계가 곧 제품 설계다. AI가 판단을 대신하지 않고 근거를 보여주는 시스템을 만들면서, 그 시스템을 설명하는 문서가 근거 없는 주장을 하면 안 되기 때문이다.
